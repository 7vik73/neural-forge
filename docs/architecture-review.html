Keep run recovery inside the execution module

Strong · corrected local-substitutable

apps/backend/src/engine.ts · runtime.ts
BeforePostgreSQL run → one queue delivery → stranded run after queue loss
AfterPostgreSQL run → execution reconciliation → durable outbox → repeatable queue delivery

Problem: Queue delivery success was mistaken for execution progress.

Solution: Reconstruct dispatches from unfinished runs and pending nodes through one execution interface.

  • Locality: recovery rules stay together
  • Leverage: restarts and queue loss share recovery

Bind schedule occurrences to published versions

Strong · corrected local-substitutable

apps/backend/src/runtime.ts · engine.ts
BeforeOld schedule job → current workflow version
AfterVersioned occurrence → version check under lock → matching run

Problem: A retained schedule job could cross the version seam.

Solution: Carry a version identity and check it atomically before creating a run.

  • Version invariants stay local
  • Obsolete occurrences are rejected

Compile AI proposals through one graph interface

Strong · corrected local-substitutable

apps/backend/src/ai.ts · packages/workflow
BeforeModel JSON → caller-supplied IDs and wiring → inconsistent graph
AfterTyped proposal → unique-ID compiler → graph validation → editable draft

Problem: Small local models made callers responsible for graph details.

Solution: Keep ID allocation, references, defaults, and validation inside the proposal implementation.

  • Leverage: one compiler for every proposal
  • Locality: repair and validation concentrate

Share one Telegram inbox across subscribers

Strong · corrected local-substitutable

apps/backend/src/polling.ts · prisma/schema.prisma
BeforeWorkflow A cursor → provider acknowledgement ← Workflow B cursor
AfterShared source checkpoint → transactional fan-out → independent runs

Problem: Provider acknowledgement semantics leaked into each workflow.

Solution: One polling implementation owns the source position and commits subscriber runs with it. Telegram connections reject duplicate tokens, reset the source cursor on token replacement, and compare credential snapshots before committing in-flight results.

  • Locality: acknowledgement rules stay together
  • Leverage: one inbox feeds many workflows
