Independent architecture review · 22 October 2026

Accounts and private workspaces

The single-owner engine now supports invited accounts with several private workspaces each. Administrator access manages accounts and installation settings without granting content access to another owner’s workspace.

Chosen architecture

Before

One owner session → installation-wide feature services → shared automation records and local folder.

Ownership was implicit. Every additional account would have needed its own filtering conventions.

After

Account session → workspace authorization → mandatory context and fenced persistence → automation services.

Queue job → persisted execution target → the same workspace context. Composite foreign keys preserve the boundary in PostgreSQL.

Small interfaces: withWorkspace, owned, WorkspaceFiles, backup/restore.

This deepens the persistence and storage modules. Callers receive one clear workspace interface; ownership checks stay local to the boundary and remain active inside transactions. No context fails closed. The explicitly named system client is restricted to initial target resolution, account administration, migration and maintenance.

Module seams and leverage

Module Interface and hidden behavior Evidence
Accounts Invitations, session issuance, lifecycle and recovery. User-row locking serializes password checks, session creation and revocation; an administrator lock protects the last active admin. Single-use/expired tokens, concurrent recovery/login, password replacement, last-admin and suspension tests.
Workspace context Request/worker context fences automation reads and writes, nested IDs and transactions. Context is outside the portable graph. Known-ID API attacks, same-owner boundaries, no-context errors, composite FK rejection and forged queue payload tests.
Storage and lifecycle Server-generated folder identities; confined file adapter; 30-day trash; cancellation and lease settlement before purge; verified resumable legacy copying. Directory isolation/traversal, trash/restore/purge, expiry cleanup, source-preserving migration tests.
Backups Private workspace archives exclude account state. Import remaps typed references and IDs, re-encrypts credentials, disables workflows and preserves history without resuming it. Encrypted round-trip, fresh identities, no credentials/account-state crossover and restored-run retry rejection.
UI navigation Workspace URLs and a save-before-switch boundary. Account, workspace and installation settings have distinct ownership. Invitation journey, separate tabs, independent notes/connections, pending edit switch, trash and restoration browser checks.

Review findings and corrections

Resolved P1 — recovery/session race. Earlier login verified a password before a separate session insert. Recovery could revoke sessions in the gap. Verification and insertion now hold the same user-row lock as recovery, suspension and password changes. A controlled concurrent test queues recovery ahead of an old-password login and verifies rejection with no surviving session.

Resolved P2 — restored retries with old resource IDs. Imported execution payloads are historical snapshots. Failed runs could previously retry against stale note IDs. Each imported run is now marked with restoredAt, retry is rejected by the engine, and the UI explains history-only status. New runs use the remapped workflow definition.

The reviewer withdrew an initial reconciliation concern after confirming the current throttle is keyed by workspace. The targeted follow-up confirmed both fixes and reported no further concrete issue. No confirmed cross-workspace content escape was found in the reviewed API fences, worker resolution, composite constraints or stream revocation.

Verification and remaining gates

34 unit/interface tests and 36 real PostgreSQL integration tests passed, including actual native Ollama summary and workflow generation. The Chromium suite checks the original workflow builder and the full account/workspace journey. Container production builds and typechecking pass on the development macOS ARM64 machine.

Independent review and automated checks support the implementation; clean Windows/Linux installations, AMD64 runtime, real provider-account tests, cross-machine full restore and first-time-user trials remain release gates. See the verification record.
